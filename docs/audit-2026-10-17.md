# Jarvis 기능·정확도·지연 점검

> 아래는 수정 전 점검 기록이다. 이후 적용한 수정·새 UI·DB 설계와 최신 검증은 [개편 기록](architecture-and-ux-2026-10-17.md)을 참고한다. 감사 재현 스크립트는 현재 소스의 회귀 확인용으로 갱신했다.

점검일: 2026-10-17 KST. 대상: 로컬 `main`, HEAD `7c9fb92` 및 현재 미커밋 변경 전체.
원격 서버·배포 APK와 동일한 버전인지는 확인하지 않았다. 제품 코드는 수정하지 않았고, 점검 문서와 오프라인 재현 도구만 추가했다.

## 판단

Android에는 실시간 음성, 작업별 상태 관리, 독립 작업 병렬 실행, 결과 보관, 확인 후 저장, 통신 복구의 기반이 있다. 다만 기록 정정의 검색 반영, 작업 참조 수명, 큰 결과 보관, 복구 중 취소 처리에 결함이 확인되어 안정화가 먼저 필요하다.

현재 코드만으로 음성 인식 정확도나 실제 응답 시간을 수치로 평가할 수 없다. 아래 시간은 코드 설정이며 실측 지연이 아니다. 기존 테스트 통과 기록도 실제 음성·글라스·모델 품질을 보증하지 않는다.

## 기능 현황

| 기능 | 코드 상태 | 한계 / 남은 검증 |
|---|---|---|
| Gemini Live 음성 대화 | 오디오 스트리밍, VAD, 응답 재생·중단 구현 | 소음·한국어 고유명사·발화 중단·장시간 연결 실측 필요 |
| Android STT / Whisper | 별도 인식 경로 존재 | Live와 지연 구조가 다름. 동일 조건 비교 미수행 |
| 촬영 + DB 검색 | 작업별 ID·revision, 카메라 자원 잠금, 독립 검색 실행 | 모든 작업이 병렬인 것은 아님. DB 쓰기는 직렬화 |
| 이전 결과 이어가기 | 작업 저장·조회·참조 해석·작업 UI 구현 | 기본 24시간, 최대 80개. 영구 기억이나 모든 작업의 자동 재개가 아님 |

| 통신 복구·중복 방지 | JSON outbox, idempotency 영수증 구현 | ViewModel 생존 중 복구. 앱 종료 중 OS 작업 없음. 복구 취소 경쟁 조건 존재 |
| 검색 근거 | 결과 카드·사진·출처, 모델 프롬프트 구현 | 근거 존재와 답변 정확도는 별도. 잘린 JSON으로 카드가 사라질 수 있음 |
| 회의 후속 업무 | 원문 근거 필터, 후속 업무 조회, 캘린더 연결 구현 | 화면 승인·일시 입력 필요. 상대 날짜 자동 해석 미완성 |
| 얼굴로 사람 식별 | 백엔드 `/people/identify`, 얼굴 등록 API 존재 | 현재 Android 도구 연결에서 식별 호출·얼굴 이미지 등록 경로를 찾지 못함 |
| iOS | Swift 카메라·Gemini·OpenClaw 코드 존재 | Android의 신규 TaskManager/outbox/수정 승인 흐름과 동등하지 않음. 빌드·실기기 미검증 |

## 우선 수정 사항

P1은 핵심 사용 결과 또는 사용자 의도에 영향을 주는 수정, P2는 성능·품질·운영 개선이다. 아래 우선순위는 실제 장애 빈도 측정이 아닌 코드 영향도 기준이다.

### F1 · P1 · 회의 정정 후 검색 데이터가 오래된 상태로 남음

- 위치: `backend/jarvis-server/app/routers/assistant.py:85`, `:98`, `:126`.
- 새 수정 경로의 `apply_values`는 `meetings`와 `summary_embedding`만 갱신한다. 연결된 `memories.text`와 임베딩은 갱신하지 않는다.
- 기존 `routers/meetings.py:360`은 회의 수정 시 파생 기억도 갱신한다. 두 경로가 불일치한다.
- 결과: 수정 화면의 요약과 검색 본문·벡터가 달라질 수 있다. 검색 SQL이 meetings도 조인하므로 새 키워드를 전혀 찾지 못한다는 뜻은 아니지만, 오래된 본문·벡터가 유지되는 문제는 남는다. 되돌리기도 같은 경로다.
- 검증: 현재 함수 AST를 추출해 SQL 수집 커서로 실행, `UPDATE meetings`만 발생함을 확인. 실제 DB 통합 재현은 미수행.
- 수정: 회의와 파생 기억 갱신을 공용 함수로 통합하고 적용·되돌리기를 같은 트랜잭션으로 처리. 수정→검색→되돌리기→검색 통합 테스트 추가.

### F2 · P1 · 복구 중 취소해도 POST가 전송될 수 있음

- 위치: Android `tasks/DurableRequests.kt:41`, `:54`; `gemini/GeminiSessionViewModel.kt:119`.
- `recover`는 재시도 대상 여부를 한 번 확인한 후 capability GET, 실제 POST를 실행한다. GET 응답 대기 중 취소되어 revision이 바뀌어도 POST 직전 재확인이 없다.
- 검증: 현재 Kotlin 소스를 컴파일하고 OkHttp interceptor로 GET 중 eligibility를 false로 변경했는데 POST 1회 발생. 실제 서버 통신 없음.
- 이미 전송된 요청을 취소가 되돌려 주지는 않는다. 문제는 아직 POST를 보내기 전에도 취소 상태를 반영하지 않는 구간이다.
- 수정: 재전송을 task/revision별 실행 수명에 연결하고 취소와 전송 시작을 조정. 전송 직전 상태 확인과 HTTP 취소를 추가하되, 전송 이후 결과 불확실 상태는 유지.

### F3 · P1 · 작업 기록 정리가 참조 중인 원본을 삭제함

- 위치: Android `tasks/TaskManager.kt:128`, `:137`, `:262`, `:362`.
- `submit`에서 선행 작업을 검증한 다음 `prune`으로 삭제할 수 있다. 실행 시 같은 선행 작업을 재검증하면 실패한다. 다른 대기 작업이 의존하는 완료 작업도 정리 대상이다.
- 검증: 최대 보관 개수를 2로 설정, 완료 작업 두 개를 만든 뒤 첫 작업을 참조하는 새 작업 제출. 원본 삭제 및 새 작업 FAILED를 현재 소스로 재현했다. 기본 80개에서도 같은 알고리즘이다.
- 수정: 활성·승인 대기 작업이 참조하는 결과를 보존하거나 참조 대상을 별도 저장소에 복사. 만료·상한 정리 모두 의존성을 고려.

### F4 · P1 · 큰 결과가 잘못된 JSON으로 저장됨

- 위치: Android `tasks/TaskManager.kt:258`, `:339`, `:355`; `tasks/ConversationReferences.kt:53`.
- 결과 문자열을 `take(64_000)`으로 자른다. 정상 JSON도 중간에 끊겨 참조 해석이나 근거 카드 생성에서 파싱이 실패할 수 있다.
- 검증: 65,000자 본문을 포함한 정상 JSON을 반환했을 때 작업은 COMPLETED이지만 저장 결과의 JSONObject 파싱 실패를 재현.
- 복구 완료 경로는 잘림 여부 플래그도 설정하지 않는다.
- 수정: 원문은 별도 파일에 보관하고 구조를 유지한 요약·페이지 정보만 작업에 저장. 문자열 절단 대신 필드별 제한 사용.

### F5 · P1 · 촬영 신선도와 중단 처리에 빈틈

- 위치: Android `stream/StreamViewModel.kt:396`.
- 휴대폰 경로는 마지막 `videoFrame`을 사용하며 프레임 도착 시각을 검사하지 않는다. 정지된 오래된 프레임이 현재 촬영 결과로 사용될 위험이 있다.
- 글라스의 `capturePhoto()`는 `NonCancellable` 안에서 실행된다. SDK가 반환하지 않으면 작업의 20초 coroutine timeout만으로 촬영 호출 종료를 보장할 수 없고 카메라 mutex도 계속 점유한다.
- 검증: 정적 코드 검토. 실제 SDK 정지·프레임 정지 재현은 미수행.
- 수정: 원본 프레임 시각·최대 허용 나이 검사, 새 프레임 대기, SDK 세션 복구 정책 마련. NonCancellable을 단순 삭제하기 전에 SDK 취소 동작 확인.

### F6 · 기능 연결 · Android 얼굴 식별 경로 누락

- 위치: `backend/.../routers/people.py:144`, Android `openclaw/OpenClawBridge.kt:138` 및 도구 선언.
- 백엔드는 이미지 기반 식별·등록을 지원하지만 현재 Android `save_person`은 이름 등 텍스트 필드만 전송하고 `/people/identify` 호출도 없다.
- 따라서 백엔드 구현만으로 “지금 앞에 있는 사람 누구야?”가 완성됐다고 볼 수 없다.
- 수정: 최신 사진→얼굴 식별→불확실 후보 확인→사람 기록 연결의 도구 계약을 연결. 얼굴 등록도 이미지·품질 거절 사유를 전달. 실제 얼굴 평가 별도 필요.

### F7 · P2 · 검색이 불확실할 때 멈추는 기준 부족

- 위치: `backend/.../routers/memory.py:511`.
- 부분 문자열 일치에 1.15 고정 점수, 벡터 검색에는 최소 유사도 제한 없이 top-k를 반환한다. 짧거나 일반적인 질의는 관련성이 낮은 최신 기록이 앞설 수 있다.
- `_NEEDS_MIN_SCORE`는 주요 기억 검색의 무응답 기준이 아니다. 근거 카드·프롬프트만으로 잘못된 검색 후보의 선택을 막지는 못한다.
- 수정: 실제 질의 평가셋으로 Recall@k, 상위 결과 정확도, 자료 없음 판별을 측정. 날짜·사람 필터와 한국어 키워드/벡터 조합을 개선하고 필요한 경우 재정렬. 임의의 유사도 상수를 정확도 기준으로 단정하지 말 것.

### F8 · P2 · 자동 복구와 문맥 전달의 비용

- `DurableRequests.send/recover`는 파일 접근뿐 아니라 네트워크 전체를 전역 mutex로 묶는다. 느린 요청이 다른 저장·정리를 지연시킬 수 있다.
- 저장·재시도마다 `/assistant/capabilities`를 호출해 네트워크 왕복이 추가된다. 서버별 capability 캐시와 버전 무효화 고려.
- 복구는 한 건의 PendingNetworkException에서 루프를 중단하고, 주기적 고정 대기를 사용한다. 첫 요청이 반복 실패하면 뒤의 요청이 대기할 수 있다. 작업별 backoff·공정한 순회·연결 복구 이벤트 고려.
- `TaskJson.kt:28`은 최대 20개 참조를 전달하고 각 발췌는 최대 4,000자다. 발췌만 약 80,000자까지 가능하므로 토큰·문맥 예산과 현재 요청에 맞는 선택이 필요하다. 실제 요청당 크기는 미측정.
- 검색은 임베딩 생성 후 정확/벡터 쿼리를 실행하고 universal 검색은 결과별 관련 기록 조회를 수행한다. 임베딩 시간, DB 쿼리 수를 측정해 캐시·배치 조회 우선순위를 정할 것.
- `embeddings.py:16`의 초기 모델 로드는 lazy이며 락이 없어 첫 요청 지연 및 동시 초기화 위험이 있다. 준비 상태 확인·warmup·초기화 동기화 검토.

### F9 · P2 · 실시간·핸즈프리 UX의 미완성 부분

- 저장·수정·일정은 화면 확인이 필요한 설계다. 안전성은 높지만 글라스만으로 끝나는 대화 경험은 아니다.
- 회의 후속 업무의 `due_at`이 원문 근거에 그대로 포함되어야 보존된다(`followups.py`). “내일”을 ISO 날짜로 정규화한 값은 제거될 수 있다. 근거 검증과 날짜 해석을 분리하고 기준 시각·시간대를 명시해야 한다.
- `ConversationReferences`는 완료 시각이 아니라 생성 순서로 누적한다. 수정과 늦게 도착하는 검색이 엇갈리는 경우 오래된 참조가 다시 나타나는지 회귀 검증 필요.
- 같은 change를 이미 적용한 경우의 응답에는 `record_id`가 빠져 있다(`assistant.py:114`). 일반 적용 응답과 계약을 통일해야 캐시 무효화가 안정적이다.
- iOS는 신규 Android 흐름을 그대로 제공하지 않는다. 공용 API 계약과 기능별 동등성 표를 만든 뒤 포팅 필요.

## 지연: 설정값과 측정해야 할 값

| 단계 | 현재 코드 설정 / 동작 | 해석 |
|---|---|---|
| Live 발화 종료 | silenceDurationMs 700ms, prefixPaddingMs 200ms | prefix padding은 단순히 더할 지연값이 아님. 실제 종료 시점은 실측 필요 |
| Legacy 서버 VAD | silence 2,500ms | Live 경로와 구분 |
| Android STT | complete silence 2,800ms, 최종 문장 debounce 1,500ms | 단순 합계가 실제 지연이라는 뜻은 아님. 인식기 이벤트·경로 영향 존재 |
| Whisper | 종료 무음 1,100ms + 추론 + 최종 debounce | tiny 모델. 기기별 추론 시간·정확도 미측정 |
| 글라스 촬영 | 촬영 호출 전 고정 2,000ms | 명시적인 추가 대기. 프레임 신선도 기준으로 대체 검토 |
| 사진 전달 | 이미지 전달 후 350ms 대기 | 모델 처리·네트워크 시간과 별도 |
| 완료 안내 | 최근 입력/작업 갱신 후 조용한 시간 1,200ms 조건 | 사용자 발화 중 안내 충돌을 줄이는 목적. 항상 다른 대기와 직렬 합산되지 않음 |
| 저장 | capability GET 후 POST | 모델·DB 시간 외 추가 왕복 |
| 통신 복구 | 한 회차 처리 후 15,000ms 대기 | 복구 최대 지연 15초 보장 아님. 요청 처리·잠금 대기 추가 |

추천 방향은 모든 무음 대기를 일괄 축소하는 것이 아니다. Live 경로를 기준으로 발화 종료, 도구 선택, 촬영/검색, 첫 오디오 재생의 시간을 각각 측정하고 고정 대기·중복 왕복부터 줄여야 한다. 추측에 기반한 저장 실행은 정확도·취소 안전성을 악화시킬 수 있다.
